# Решения

Журнал решений, принятых при реализации `sweep`. Спека — источник истины
(`docs/sweep-spec.md`); всё, что в ней не описано и не покрыто её таблицей
«Открытые вопросы и решения по умолчанию», записывается здесь.

| 2026-10-17 | `mode` по умолчанию — `contents` | В спеке умолчание для `mode` не названо (в отличие от `kind`). Во встроенных правилах каталоги-кэши — `%LOCALAPPDATA%\CrashDumps`, `SoftwareDistribution\Download`, `%LOCALAPPDATA%\pnpm\store`, `%USERPROFILE%\.gradle\caches` — перечислены без `mode`, то есть по смыслу чистится их содержимое | Правило без `mode` удалит не то: содержимое каталога вместо самого объекта (или наоборот) |
| 2026-10-17 | `min_size`: суффиксы `B/KB/MB/GB/TB` — степени 1024 | Спека пишет только «строка вида `50MB`»; 1024 совпадает с тем, как Проводник показывает размеры, и с ожиданием автора правила | Порог отбора файлов разойдётся с ожиданием автора правила |
| 2026-10-17 | `rules.Error` (`файл:строка:столбец`) заведён в этапе 1 вместе с загрузчиком | Загрузчик — первый, кто обязан назвать место: `min_size: 50XB` — ошибка формата, её нельзя прочитать и отложить до валидации | Ничего: тот же тип переиспользуют проверка схемы и смысловые проверки |
| 2026-10-17 | Схема формата — JSON Schema draft 2020-12 с `additionalProperties: false` на каждом уровне и `minItems: 1` у `targets` | Спека требует «неизвестные поля — ошибка»; целевой список из нуля целей — правило, которое ничего не делает молча, а ошибка честнее | Правило с `targets: []` станет ошибкой там, где автор ожидал «ничего не делать» |
| 2026-10-17 | Пакеты-носители `schema` и `rules` в корне репозитория | `go:embed` не берёт файл из родительского каталога, а спека фиксирует пути `schema/rule.schema.json` и `rules/...`; альтернатива — дублировать файлы | Два маленьких публичных пакета вместо правила «всё в `internal`» |
| 2026-10-17 | Сообщения схемы берутся у `jsonschema/v6`, `golang.org/x/text` становится прямой зависимостью | Библиотека отдаёт готовый текст только через локализованный принтер; свои сообщения на каждый вид ошибки — дублировать её словарь | Ещё одна прямая зависимость; замена на свои сообщения — один файл |
| 2026-10-17 | Неизвестные поля сообщаются по одному на поле, позиция — сам ключ; находки сортируются по позиции | Библиотека перечисляет все лишние поля одного маппинга одним сообщением и в порядке, который не совпадает с порядком в файле | Вывод отличается от «как у библиотеки», зато правка файла идёт по одной подсказке за раз, а порядок вывода предсказуем |
| 2026-10-17 | Согласованность `kind` с `path`/`cmd`/`args` — смысловая проверка этапа 1, а не схема | В таблице целей спеки обязательности полей нет, а сообщения `not` и `false schema` у библиотеки нечитаемы («'not' failed»); свои формулировки лучше | Проверка живёт в смысловом шаге, а не в схеме, и её не увидят редакторы по `$schema` |
| 2026-10-17 | Язык масок живёт в `platform`: `CompileMask` переводит маску в регулярное выражение; разделитель — разделитель, а не escape; метасимволы — `*`, `**`, `?` | Спека задаёт маску как путь Windows с `*`, `**` и `?`. `path.Match` трактует `\` как escape, поэтому путь, записанный как в таблице встроенных правил спеки (`...\User Data\*\`), не компилировался, а `\*` молча значил литеральную звёздочку (нашло ревью этапа 1). Ни один из трёх метасимволов не встречается в именах Windows, поэтому маске не нужен escape и грамматика остаётся однозначной. Проверка и обход файловой системы (`platform.Glob` этапа 2) берут компилятор из одного места | В грамматике спеки компилируется любая непустая маска, так что проверка ловит только пустую; символьные классы (`[a-z]`) не поддерживаются — `[` остаётся литералом |
| 2026-10-17 | `platform.Env` и `OSEnv` лежат в `internal/platform` без build-тега | Спека держит под тегом `windows` только WinAPI (`FS`, `Procs`, корзина); `os.LookupEnv` отвечает на тот же вопрос на любой платформе, а тесты `internal/rules` идут и на ubuntu-CI | Ничего |
| 2026-10-17 | Конфиг (`rules/config.go`) не имеет JSON Schema: разбирается руками теми же помощниками, что и правила (`field`, `errorAt`), и сам проверяет форму значений | Спека задаёт поля конфига строчкой текста, схемы у него нет; ручной разбор даёт те же позиционные сообщения, что и у правил, и не тянет вторую схему ради четырёх полей | Каждое новое поле требует и чтения, и проверки формы руками; забытая проверка тихо пропустит значение |
| 2026-10-17 | `profile.DefaultOnly` — только для встроенных профилей: в профиле из конфига ключ `default_only` отвергается как неизвестное поле | Спека перечисляет поля профиля закрытым списком (`include`, `include_tags`, `include_categories`, `max_risk`, `exclude`), а `DefaultOnly` не выражается ими — он нужен встроенным `default` и `dev` | Пользователь не может написать профиль «встроенный default плюс мои маски»; обходной путь — перечислить маски в `include` |
| 2026-10-17 | `rules.Set` несёт поле `Toggles map[string]model.RuleToggle` (в плане было `{Rules, Profiles, Warnings}`) | Выключатель конфига действует поперёк профилей: `enabled: false` убирает правило, о котором профиль молчит, а `enabled: true` возвращает то, что профиль не выбрал. `Select(set, имя)` конфига не видит, поэтому переключатели едут в наборе | Ещё одно поле в наборе и обязанность `Select` его учитывать |
| 2026-10-17 | `id`, повторённый в одном источнике, — ошибка; тот же `id` из более позднего источника — замена с предупреждением | Спека говорит и то («`id` не повторяется внутри источника», строка 132), и другое («правило с тем же `id` из более позднего источника заменяет предыдущее целиком», строка 127). Внутри источника ни один файл не главнее другого, между источниками порядок задан | Два файла в `%APPDATA%\sweep\rules` с одним `id` останавливают запуск — придётся убрать дубль вручную |
| 2026-10-17 | Отсутствующий `--rules-dir` — ошибка, отсутствующий пользовательский каталог — нет | Пользовательский каталог пуст на чистой машине, и это норма; каталог, названный флагом, назван осознанно, и молча его терять нельзя | Правило из опечатанного пути не подхватится без сообщения (только по флагу) |
| 2026-10-17 | `Toggles` с чужим `id` и профиль из конфига с именем встроенного дают предупреждение, а не ошибку | Конфиг может опережать правила (правило появится позже) или намеренно менять встроенный профиль; предупреждение видно, но не мешает работать | Шум в предупреждениях, если конфиг ведёт список выключенных правил «на будущее» |
| 2026-10-17 | Порядок в `rules.Select`: `exclude` перекрывает всё, выключатель конфига перекрывает профиль, `max_risk` применяется последним | Одно правило, которое надо выключить в профиле, должно выключаться даже при `enabled: true` в конфиге; а `max_risk` — предохранитель, и переключатель не должен его пробивать | Правило с `enabled: true`, попавшее под маску `exclude` профиля, не появится; маска профиля, которая не компилируется, даёт предупреждение и не выбирает ничего |
| 2026-10-17 | Объявлены коды возврата 0/1/2; коды 3 (нужно подтверждение без терминала) и 4 (частично) ждут своих команд | Спека перечисляет четыре кода, но у 3 и 4 пока нет потребителя: их возвращают `clean` и исполнитель этапов 4–5. `cli.ExitError` заводится здесь, потому что кодом 2 заканчиваются ошибки флагов, конфига и правил | Маппинг остальных кодов добавится вместе с командами, которые их возвращают |
| 2026-10-17 | `--config` и `--rules-dir` — постоянные флаги корня, а `--profile`, `--json`, `--category` объявлены у команды `list` | Спека даёт `--config`/`--rules-dir` всем командам, а `--profile`/`--json` — `scan`, `clean`, `list`; из них существует только `list`. Флаг, который команда молча игнорирует, хуже, чем объявить его второй раз, когда появится `scan` | При появлении `scan`/`clean` флаги переедут в постоянные, а `list` их унаследует |
| 2026-10-17 | Синтаксис `%ПЕРЕМЕННЫХ%` и их раскрытие живут в `platform` (`EnvNames`, `Expand`), и в имени допускаются скобки | Синтаксис нужен двум местам: смысловая проверка ищет неизвестные переменные, а `rules show` раскрывает их для отладки путей. Windows сам заводит `%ProgramFiles(x86)%`, и без скобок такая переменная молча осталась бы текстом | Раскрытие не понимает `%VAR:~1,2%`-подстановок cmd — если понадобятся, это отдельная работа |
| 2026-10-17 | Пустая маска в `include`/`exclude` — ошибка смыслового прохода; пустой `path` оставлен схеме (`minLength: 1`) | Ревью этапа 1 спросило, что значит пустая маска: она не берёт ничего и молчит об этом, а пустой путь уже отвергает схема — два прохода на один дефект дали бы две находки на одном месте | Файл правил, намеренно написавший пустую маску, будет отвергнут |
| 2026-10-17 | `rules validate` отдаёт находки ошибкой команды: cobra печатает их в stderr один раз, stdout остаётся пустым | Находки с позициями — диагностика, как у компилятора или `go vet`, и место ей в stderr; печать их самим и возврат той же строки ошибкой дублировала бы каждый текст, а «отчёт» в stdout мешал бы читать stdout как ответ команды | Скрипт, читающий stdout, у `rules validate` не увидит ничего — и находки, и предупреждения идут в stderr |

## Ревью этапа 1

Ревью этапа 1 (коммиты `3235df7..b29d6ac`) нашло одно критичное замечание и три важных. Исправлено по их итогам:

| Замечание | Что сделано |
| --- | --- |
| Маски читались диалектом `path.Match`: путь с завершающим `\` (как в таблице встроенных правил спеки) отвергался, а `\*` молча значил литерал | Компилятор масок переехал в `platform` (`CompileMask`), им же пользуется смысловая проверка и `Select` профиля — см. строку о языке масок |
| Ошибка разбора YAML не имела позиции | `syntaxError` достаёт строку из сообщения парсера, столбец — начало этой строки; `файл:строка:столбец` теперь у любой ошибки |
| `rules validate <каталог>` падал с «Incorrect function» Windows и называл путь дважды | Каталог читается как набор `*.yaml` в порядке имён; путь, который не открылся, сообщается один раз — так, как его назвала система |
| Смысловой проход добавлял вторую находку на цель-не-объект («a path target takes path» поверх ошибки схемы) | Не-маппинг отдан схеме; на каждый дефект — одна находка, и это закреплено тестом по всем фикстурам невалидного набора |
| Повторённый ключ конфига молча брал последнее значение | Повторённый ключ и повторённая запись (`rules.<id>`, профиль) — ошибка с позицией |
| `dataDir()` брал `%APPDATA%` через `os.Getenv` и при отсутствии молча давал относительный путь | `os.UserConfigDir()` называет проблему ошибкой |
| Тире в выводе `rules show` — не ASCII | Дефис: вывод должен читаться в любой консоли, включая `conhost` |
| Два прохода валидации вызывались в загрузчике и в CLI порознь | `rules.Validate(file, env)` — одна пара проходов для обоих |
| Пустая маска молча пропускалась, и решение об этом не было записано (рекомендация ревью) | Пустая маска — ошибка смыслового прохода (строка о пустой маске выше), фикстура `invalid/empty-include-mask.yaml`, и число находок на каждую фикстуру закреплено тестами |
| Разбор конфига — единственный вход без схемы, ревью предложило fuzz | `FuzzLoadFile` и `FuzzLoadConfig`: 30 секунд каждый на этой машине без падений |

Осознанно отложено по итогам этого ревью:

| Мелочь | Почему отложена |
| --- | --- |
| Предупреждения прогона теряются, если в том же прогоне нашлись ошибки: `Loader.Load` возвращает `nil` набор, а предупреждения живут в нём | Нужен отдельный «отчёт о проверке», возвращающий находки и предупреждения раздельно; до тех пор исправленная ошибка показывает предупреждения при повторном запуске, а `rules validate <файл>` их не теряет |
| Короткий fuzz-прогон на каждый pull request (спека, раздел «Тестирование и CI») в CI не заведён | Цели `FuzzLoadFile`/`FuzzLoadConfig` есть, но джоба в `.github/workflows/ci.yml` — вопрос этапа 2, где fuzz требует `guard` (спека, строка 529) |

## Открытые мелочи после этапа 0

Ревью этапа 0 (коммиты `2bb192b..e644c63`) не нашло критичных замечаний. Исправлено по итогам ревью: пин версии линтера в CI (`v2.15.0` вместо `latest`) и разделение stdout/stderr в тестах `internal/cli` — тест не мог отличить вывод версии в правильный поток от вывода в stderr.

Осознанно отложено:

| Мелочь | Почему отложена |
| --- | --- |
| `sweep --help` обещает TUI, `scan` и `clean` в настоящем времени, хотя их ещё нет | Косметика текста; поведение появится на этапах 3–5, тогда справка станет правдой |

| Любая ошибка даёт код возврата 1, спека отводит 2/3/4 | Этап 1 завёл коды 0/1/2 (2 — ошибка флагов, конфига и правил); 3 и 4 ждут команд, которые их возвращают |
| Дефолтная команда cobra `completion` в таблице команд спеки отсутствует | Стандартное поведение cobra, выключается одной строкой |
| Линт можно вынести в отдельную джобу и запускать параллельно тестам | Оптимизация времени CI, спека этого не требует |
| Первый прогон CI не наблюдался ни разу | `push` в этапе 0 не делался: локальные `gofmt`/`go vet`/`go test`/`golangci-lint` зелёные, но `windows-latest` и `ubuntu-latest` проверяются только после первого `push` |
