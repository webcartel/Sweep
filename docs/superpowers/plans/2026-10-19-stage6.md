# Stage 6 — Full builtin rule set and docs — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans
> (the project's established execution mode; sessions run inline, one leader
> per session, small commits).

**Goal:** Ship the 26 builtin rules from the spec table, verified on this
machine (Win 10 Pro for Workstations 22H2, build 19045), plus
`docs/rules.md`, `docs/format.md`, `CONTRIBUTING.md`, and the TUI screenshot
in the README — the v1 release milestone.

**Architecture:** Rules are data only — new YAML files under `rules/`, picked
up by the existing `go:embed` in `internal/rules`. The verification work is
reading real directories with PowerShell and writing the result into
`docs/rules.md`. No changes to Go code are expected; if one turns out
necessary, the task stops and asks instead of improvising.

**Tech Stack:** Go 1.27 (no new dependencies), YAML rule files (schema 1),
Markdown docs, PowerShell for read-only path verification.

**Spec:**
- `docs/sweep-spec.md` — table «Встроенные правила v1» (lines 493–518 = 26
  rules; the «20» in the done-when text is a spec miscount, ruling below);
  «Этап 6» (line 607).
- `docs/superpowers/specs/2026-10-19-stage6-design.md` — the approved design.

## Global Constraints

- Risk, `default_enabled`, admin (`RequiresAdmin`), `tags: [dev]` — exactly
  as in the spec table, cell by cell.
- Interface and rule names/descriptions in English; working docs
  (`docs/rules.md`, `docs/format.md`, `CONTRIBUTING.md`) in English;
  `docs/decisions.md` stays Russian.
- Probe paths read-only with PowerShell; nothing is deleted without the
  user's word.
- Win 11 column: `not verified` for every rule (user decision).
- A rule whose path is proven wrong on this machine is removed from the set;
  an absent app with a vendor-documented path layout stays
  `not verifiable here` (design ruling).
- Every commit: `gofmt`, `go vet ./...`, `golangci-lint run`,
  `go test ./...` green; ledger in
  `.superpowers/sdd/2026-10-19-stage6/progress.md`.
- No push without asking.

## Review Focus

Failure modes this stage implies that task tests do not cover:

1. **A `mode: contents` target pointing at a file** (e.g. `*.log`,
   `MEMORY.DMP`): contents on a file must be a skip, never a recurse-fail —
   pinned by the cbs-logs/minidumps rules' unit test in `internal/rules`.
2. **A command rule's binary missing** (`docker` not installed): scan must
   mark the rule out-of-scope, not error — exercised by existing executor
   tests; verify against the real rules with `sweep scan --json` on a
   machine without docker.
3. **A rule touching a guard-protected tree** (`%SystemRoot%\Temp`,
   SoftwareDistribution): guard must still refuse targets outside the
   narrowed path — pinned by the rule-set test that runs disclosed paths
   through the guard.
4. **Duplicate or typoed IDs across 8 files** (embed swallows new files
   silently): the rule-set test asserts unique IDs and the exact set of
   26 IDs.
5. **`docs/rules.md` drifting from the actual set**: every rule ID in
   `sweep list --json` appears in rules.md — checked manually at Task 5's
   verification step.
